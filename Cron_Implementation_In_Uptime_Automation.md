# Linux Cron Automation – Daily Server Uptime Audit

## 1. Introduction

In our server uptime audit project, we initially had to execute the Bash script manually to check the uptime and system health of multiple servers.

To eliminate this repetitive task, we decided to automate the execution using **Linux Cron**.

Our objective was to configure the script to execute automatically every day at **11:15 AM**, without requiring manual intervention.

### What is Cron?

Cron is a time-based job scheduler available in Linux and Unix-like operating systems.

It allows us to schedule commands and scripts to execute automatically at predefined times or intervals.

Some common use cases include:

- Running daily backup scripts.
- Monitoring server health.
- Generating periodic reports.
- Cleaning temporary files.
- Running database maintenance tasks.
- Executing scheduled automation scripts.

### What is Crontab?

Crontab stands for Cron Table.

It contains the scheduled jobs that Cron executes.

We can manage scheduled jobs using:

```bash
crontab -e
```

To display existing scheduled jobs:

```bash
crontab -l
```

To remove all scheduled jobs belonging to the current user:

```bash
crontab -r
```

**Important:** `crontab -r` removes the user's entire crontab. We should not execute it unless we intentionally want to remove all scheduled jobs.

## 2. Understanding Cron Expression Syntax

A standard Cron expression consists of five time fields followed by the command to execute.

```text
┌───────────── minute (0–59)
│ ┌───────────── hour (0–23)
│ │ ┌───────────── day of month (1–31)
│ │ │ ┌───────────── month (1–12)
│ │ │ │ ┌───────────── day of week (0–7)
│ │ │ │ │
* * * * * command
```

### Understanding Each Field

| Field | Allowed values | Description |
|---|---|---|
| Minute | 0–59 | At which minute the job executes |
| Hour | 0–23 | At which hour the job executes |
| Day of month | 1–31 | On which date the job executes |
| Month | 1–12 | During which month the job executes |
| Day of week | 0–7 | On which weekday the job executes (Sunday can be 0 or 7) |

### Understanding Special Characters

| Symbol | Meaning | Example |
|---|---|---|
| `*` | Every possible value | Every day |
| `,` | Multiple specific values | `1,15` |
| `-` | A range of values | `1-5` |
| `/` | An interval | `*/5` |

### Practical Cron Examples

```bash
*/5 * * * *       # Every 5 minutes
0 * * * *         # Every hour
30 9 * * *        # Every day at 9:30 AM
15 11 * * *       # Every day at 11:15 AM
0 10 * * 1-5      # Monday to Friday at 10 AM
0 0 * * *          # Every day at midnight
```

## 3. Understanding Standard Linux File Descriptors

Before configuring our Cron job, we need to understand how Linux handles input and output.

Whenever a Linux process executes, it normally has three standard file descriptors.

| File Descriptor | Name | Purpose |
|---|---|---|
| `0` | stdin | Standard input |
| `1` | stdout | Standard output |
| `2` | stderr | Standard error |

### 3.1 Standard Input (stdin)

File descriptor `0` represents standard input.

It is used when a command receives input from the keyboard, a file or another process.

Example:

```bash
read -p "Enter your name: " name
```

Here, the command receives input from the user.

### 3.2 Standard Output (stdout)

File descriptor `1` represents standard output.

It carries normal output generated by a command.

Example:

```bash
ls /home
```

The directory listing is sent to stdout and normally displayed in the terminal.

### 3.3 Standard Error (stderr)

File descriptor `2` represents standard error.

It carries error messages generated by a command.

Example:

```bash
ls /directory-that-does-not-exist
```

The resulting error message is sent to stderr.

### Visual Representation

```text
                 Linux Process
                      |
          +-----------+-----------+
          |           |           |
        stdin       stdout      stderr
          0            1           2
          |            |           |
        Input        Normal       Error
                    Output       Messages
```

An important point is that stdout and stderr are separate streams, even though both normally appear in our terminal.

## 4. Understanding Output Redirection

Linux allows us to redirect command output from the terminal to files or other destinations.

### 4.1 Redirect Standard Output

```bash
ls /home > output.log
```

Here:

- `>` is the output redirection operator.
- `output.log` is the destination file.
- By default, `>` redirects stdout (file descriptor 1).
- If the file does not exist, it is created.
- If the file exists, its previous contents are overwritten.

The following command performs the same operation explicitly:

```bash
ls /home 1> output.log
```

### 4.2 Redirect Standard Error

```bash
ls /directory-that-does-not-exist 2> error.log
```

Here:

- `2` represents stderr.
- `>` redirects the error output.
- `error.log` stores the error message.

### 4.3 Append Output Instead of Overwriting

We can use `>>` when we want to append output to an existing file.

```bash
ls /home >> output.log
```

Unlike `>`, the `>>` operator does not overwrite existing content.

Similarly, we can append errors:

```bash
ls /directory-that-does-not-exist 2>> error.log
```

### Difference Between `>` and `>>`

| Operator | Behaviour |
|---|---|
| `>` | Creates a file or overwrites existing contents |
| `>>` | Creates a file or appends to existing contents |

## 5. Understanding `2>&1` in Detail

This is one of the most important concepts in our Cron configuration.

```bash
2>&1
```

Let's break it down:

| Component | Meaning |
|---|---|
| `2` | Standard error |
| `>` | Redirection operator |
| `&1` | The current destination of file descriptor 1 |

Therefore:

**`2>&1` redirects standard error to the same destination currently used by standard output.**

### Example

```bash
ls /home /invalid-directory > combined.log 2>&1
```

What happens?

1. `> combined.log` redirects stdout into `combined.log`.
2. `2>&1` redirects stderr to the current destination of stdout.
3. Both normal output and errors are written to `combined.log`.

### Visual Representation

```text
             Linux Command
                   |
           +-------+-------+
           |               |
         stdout          stderr
           1                2
           |                |
           |             2>&1
           |                |
           +-------+--------+
                   |
              combined.log
```

### 5.1 Why Does Redirection Order Matter?

Consider these two commands.

**Command A:**

```bash
ls /home /invalid-directory > output.log 2>&1
```

Both stdout and stderr go into `output.log`.

**Command B:**

```bash
ls /home /invalid-directory 2>&1 > output.log
```

Here:

- First, stderr is redirected to the current destination of stdout, which is the terminal.
- Then, stdout is redirected to `output.log`.
- Stderr remains connected to the terminal.

Therefore, only stdout goes into the file.

**Important rule:** Shell redirections are processed from left to right. The destination copied by `2>&1` depends on where stdout points when that redirection is evaluated.

### 5.2 Discarding Error Messages

Linux provides a special device called `/dev/null`.

Anything written to it is discarded.

Example:

```bash
ls /invalid-directory 2>/dev/null
```

This redirects stderr to `/dev/null`, so the error is discarded instead of being displayed or saved.

Before configuring our scheduled job, we need to verify that the Cron service is running.

```bash
systemctl status cron --no-pager
```

Expected status:

```text
Active: active (running)
```

If Cron is not installed, we can install and enable it:

```bash
apt update
apt install cron -y
systemctl enable --now cron
```

### Useful Cron Service Commands

```bash
systemctl status cron
```

Check the service status.

```bash
systemctl start cron
```

Start the service.

```bash
systemctl stop cron
```

Stop the service.

```bash
systemctl restart cron
```

Restart the service.

```bash
systemctl enable cron
```

Enable the service to start automatically during boot.

```bash
systemctl enable --now cron
```

Enable and start the service immediately.

## 8. Configuring Cron for Our Uptime Audit

Our project is located at:

```text
/opt/uptime
```

The main Bash script is:

```text
/opt/uptime/uptime_audit.sh
```

We want to execute this script every day at 11:15 AM.

### 8.1 Open the Root User's Crontab

Since we want the job to execute as root, we open root's crontab.

```bash
crontab -e
```

The first time we execute this command, the system may ask us to select an editor.

Example:

```text
Select an editor. To change later, run select-editor.

1. /bin/nano
2. /usr/bin/vim.basic
3. /bin/ed

Choose 1-3 [1]:
```

We selected Nano by entering:

```text
1
```

Then pressed Enter.

**Important:** We must enter the editor selection number first. We should not paste our Cron expression at this prompt.

### 8.2 Add the Cron Expression

Once the Nano editor opens, we add:

```bash
15 11 * * * cd /opt/uptime && /opt/uptime/uptime_audit.sh >> /opt/uptime/cron_execution.log 2>&1
```

### 8.3 Save the Crontab

In Nano:

| Keyboard shortcut | Action |
|---|---|
| `Ctrl + O` | Save the file |
| `Enter` | Confirm the filename |
| `Ctrl + X` | Exit Nano |

### 8.4 Verify the Configuration

```bash
crontab -l
```

Expected entry:

```bash
15 11 * * * cd /opt/uptime && /opt/uptime/uptime_audit.sh >> /opt/uptime/cron_execution.log 2>&1
```

## 9. Breaking Down Our Complete Cron Command

Let's understand every part of the command we configured.

```bash
15 11 * * * cd /opt/uptime && /opt/uptime/uptime_audit.sh >> /opt/uptime/cron_execution.log 2>&1
```

### Part 1: Scheduling Fields

```bash
15 11 * * *
```

| Field | Value | Explanation |
|---|---|---|
| Minute | `15` | At minute 15 |
| Hour | `11` | At 11 AM |
| Day of month | `*` | Every date |
| Month | `*` | Every month |
| Day of week | `*` | Every weekday |

Result: Execute every day at 11:15 AM.

### Part 2: Change Directory

```bash
cd /opt/uptime
```

This changes the working directory to our project directory.

This is important because our Bash script uses relative paths, including:

- `vincentio_servers.txt`
- `server_uptimes.log`

Cron does not automatically start in our project directory.

### Part 3: Logical AND Operator

```bash
&&
```

This operator executes the next command only if the previous command succeeds.

Therefore, if changing to `/opt/uptime` fails, our audit script will not execute.

### Part 4: Execute the Bash Script

```bash
/opt/uptime/uptime_audit.sh
```

This executes our server uptime audit script.

### Part 5: Redirect Standard Output

```bash
>> /opt/uptime/cron_execution.log
```

This appends the script's standard output to `cron_execution.log`.

If the file does not exist, it is automatically created.

### Part 6: Redirect Standard Error

```bash
2>&1
```

This redirects standard error to the same destination as standard output.

Therefore, both normal output and error output are captured in:

```text
/opt/uptime/cron_execution.log
```

### Complete Command Flow

```text
Cron Scheduler
      |
      | Every day at 11:15 AM
      |
      v
cd /opt/uptime
      |
      | If successful
      v
Execute uptime_audit.sh
      |
      +---------------------+
      |                     |
      v                     v
    stdout                stderr
      |                     |
      |                  2>&1
      |                     |
      +----------+----------+
                 |
                 v
        cron_execution.log
```

## 10. Understanding Our Two Log Files

We use two separate log files for different purposes.

### 10.1 server_uptimes.log

Location:

```text
/opt/uptime/server_uptimes.log
```

Purpose:

This file contains the actual audit results collected from remote servers.

It includes information such as:

- Server uptime.
- Disk usage.
- RAM usage.
- System load.
- Temperature, when available.
- Health status and alerts.

To view the latest entries:

```bash
tail -n 50 /opt/uptime/server_uptimes.log
```

### 10.2 cron_execution.log

Location:

```text
/opt/uptime/cron_execution.log
```

Purpose:

This file captures the standard output and standard error produced when Cron executes our Bash script.

To view its contents:

```bash
cat /opt/uptime/cron_execution.log
```

To monitor it continuously:

```bash
tail -f /opt/uptime/cron_execution.log
```

To monitor it with periodic refreshes:

```bash
watch -n 5 cat /opt/uptime/cron_execution.log
```

### Difference Between the Two Files

| File | Purpose |
|---|---|
| `server_uptimes.log` | Actual server audit results |
| `cron_execution.log` | Script execution output and errors |

These logs serve different purposes and should not be confused.

## 11. Testing Our Cron Job Immediately

We did not want to wait until the following morning to verify whether Cron was working.

Therefore, we temporarily changed the schedule to a time a few minutes ahead.

For example, to execute at 2:32 PM:

```bash
32 14 * * * cd /opt/uptime && /opt/uptime/uptime_audit.sh >> /opt/uptime/cron_execution.log 2>&1
```

Remember that Cron uses the 24-hour clock.

| Time | Cron hour |
|---|---|
| 9 AM | `9` |
| 11 AM | `11` |
| 2 PM | `14` |
| 5 PM | `17` |
| 8 PM | `20` |

### Testing Procedure

1. Open root's crontab.

```bash
crontab -e
```

2. Set a temporary execution time.

```bash
32 14 * * * cd /opt/uptime && /opt/uptime/uptime_audit.sh >> /opt/uptime/cron_execution.log 2>&1
```

3. Save and exit Nano.

4. Wait until the scheduled time.

5. Check the execution log.

```bash
cat /opt/uptime/cron_execution.log
```

6. Check the actual audit results.

```bash
tail -n 65 /opt/uptime/server_uptimes.log
```

7. Check Cron execution records.

```bash
grep CRON /var/log/syslog | tail -n 20
```

### What We Look for in the Syslog

Our actual test produced this entry:

```text
2026-11-05T14:32:01.976377+05:30 ubuntu CRON[11406]: (root) CMD (cd /opt/uptime && /opt/uptime/uptime_audit.sh >> /opt/uptime/cron_execution.log 2>&1)
```

This confirmed that:

- Cron triggered the job at 14:32:01.
- The job ran under root.
- Our project directory was selected.
- The Bash script was executed.
- Output redirection was configured.

### Actual Execution Log

Our test produced output similar to:

```text
Starting daily uptime audit. Please wait...

Audited [SERVER - MANAGEMENT] -> Check log for dashboard.
Audited [SERVER - UP-LIFT1] -> Check log for dashboard.
Audited [SERVER - UP-LIFT2] -> Check log for dashboard.

----------------------------------------
Audit complete. Check server_uptimes.log for details.
```

This demonstrated that the scheduled execution completed its audit workflow.

**Important distinction:** A successful Cron execution does not guarantee that every remote server is reachable. In our test, some servers returned connection timeouts, but Cron still successfully launched the script.

## 13. Important Points to Remember

### 13.1 The Machine Must Be Running

Cron can execute the job only when:

- The machine is powered on.
- The Cron service is running.
- The scheduled time is reached.

A normal Cron job will not automatically execute a missed schedule after a machine has been powered off. Anacron or a suitable systemd timer can be considered if catch-up execution is required.

### 13.2 Cron Uses the System Timezone

Always verify the timezone when scheduling jobs.

```bash
timedatectl
```

### 13.3 Use Absolute Paths

Cron runs with a different environment from an interactive terminal.

Using absolute paths helps prevent problems related to the current directory and executable search path.

### 13.4 Run Under the Correct User

We configured our job using:

```bash
crontab -e
```

while logged in as root.

Therefore, it runs under the root account.

A regular user's crontab would execute under that user's permissions instead.

### 13.5 Protect Sensitive Files

Our inventory contains server connection credentials.

We should not expose the real inventory or production audit logs in a public GitHub repository.

Restrict access to the inventory file:

```bash
chmod 600 /opt/uptime/vincentio_servers.txt
```

Also ensure that generated logs do not expose sensitive infrastructure information.
